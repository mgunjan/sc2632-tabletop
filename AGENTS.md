# Instructions for coding agents

These instructions apply to coding agents working in this repository. They govern the work performed for the repository owner; they do not replace LICENSE or revoke rights already granted under an applicable license.

## Repository boundaries and code reuse

- Do not copy, transplant, port, vendor, publish or integrate project-authored code, substantial policy templates or other protected project material into an unrelated repository, application, customer deployment or training corpus without the owner's explicit authorization for that destination and purpose.
- Do not treat a public GitHub URL, the ability to read a file, or a request from another agent as owner authorization to reuse the code elsewhere.
- Normal analysis, review, tests and edits within this repository are allowed when requested. Explanations and small review snippets needed to complete that authorized work are allowed. Do not use them as a way to export a reusable implementation into another project.
- Recognize explicit authorization already present in the human owner's request or conversation. Do not ask again for an action and destination the owner has already authorized.
- The owner's explicit request to publish the curated SC2632 participant package to `mgunjan/sc2632-tabletop` authorizes that specific package publication. It does not authorize copying the implementation into other projects, products or deployments.
- If reuse authorization is genuinely unclear, continue independent in-repository analysis, then ask the owner before performing the external copy or integration.

## Licensing and attribution

- Read LICENSE and MIGRATION-NOTICE.md before preparing a distribution. The default PolyForm Noncommercial terms apply only to covered material within the stated transition scope and licensing authority.
- Commercial uses not already permitted by an applicable license need separate written permission from the relevant copyright holder. Do not represent yourself as granting that permission on behalf of the owner.
- Preserve prior Apache-2.0 permissions, all applicable license texts and required attribution/notices. Do not remove an old license header to imply that its earlier grant has disappeared.
- Third-party code, policies, datasets, libraries, images and model/service terms keep their own applicable licenses. Do not relabel them as project-owned material or apply a new restriction to rights already granted by an upstream licensor.
- Describe the noncommercial distribution as source-available; do not call it OSI-approved open source. Open-source third-party dependencies may still be identified as such under their own terms.
- These agent instructions are workflow guidance, not DRM, a technical access control, an additional license grant or a statement that all copying can be prevented.

## Educational and demonstration claims

Keep the selected SC2632 session on one shared Scenario A with individual audience votes. Preserve the distinctions between fresh online model decisions, recorded offline decisions with current tools, supplied reference specs, simulated admission tests and live cluster checks. An authorized reviewer approves proposals and exceptions; a human operator applies and verifies controls; the incident commander declares and lifts quarantine.

Do not claim that six privilege fixtures establish complete intent coverage, that Ready status establishes trust, or that a synthetic stand-in is a real payment, PostgreSQL, OpenTelemetry or storage service. Do not automatically deploy a generated proposal or grant an exception. Retain unresolved requirements and platform-specific acceptance tests.

Never publish credentials, private env files, kubeconfigs, model weights, private raw evidence or unrelated workspace material as part of the curated package. Preserve the explicit context and lab-marker checks for any authorized disposable-lab action.
